# Design: 技能/攻击距离显示与棋将包系统

## Context

- **当前状态**：FightBoard 通过 `GetEnemyCellsInAttackRange` 仅返回「攻击范围内且格内有敌将」的格子，ChessHero 在选择攻击/技能时用该结果调用 `SetHighlightCells`，故高亮与可点击执行均限定在「有目标的格子」。无布阵阶段，测试场景通过静态 `HeroConfigIds` 直接在场内生成棋将。
- **约束**：沿用 Godot 4 + C#、Excel 配置（General.xlsx）、现有 FightBoard/ChessHero/GeneralConfigLoader API；不引入新运行时依赖。
- **相关方**：战斗流程与棋盘交互在 FightBoard/ChessHero；棋将配置与列表来自 GeneralConfigLoader；布阵需与现有回合/战斗开始衔接。

## Goals / Non-Goals

**Goals:**

- 选择攻击/技能后高亮**所有**在攻击距离内的格子；仅当玩家点击的格子内存在可攻击目标时才执行攻击/技能，点击范围内空格子则不执行（或取消选择）。
- 战斗前增加布阵阶段：战斗场面下方显示棋将包，包内棋将从 General.xlsx 加载；玩家可拖拽棋将到地图第 1 列或第 2 列，点击「确认出战」后开始战斗；每场战斗每个棋将只能被拖拽上场一次。

**Non-Goals:**

- 不改变攻击/技能伤害或范围的计算方式；不在本变更内实现「本关可用棋将」子集配置（可选：由 General.xlsx 全表或后续关卡表扩展）。
- 棋将包不实现多页/筛选/排序等复杂 UI；拖拽仅支持放到第 1/2 列的空位。

## Decisions

1. **攻击范围高亮与执行判定的数据分离**  
   - **决策**：FightBoard 提供两种能力：(1) 按曼哈顿距离返回「攻击范围内的所有格子」`GetCellsInAttackRange(row, col, range)`；(2) 保留或复用「范围内且格内有敌将的格子」用于执行判定。ChessHero 选择攻击/技能时用 (1) 做高亮，点击格子时用 (2) 或「格内有敌将」判断是否执行。  
   - **理由**：高亮与可执行语义分离后，UI 先展示完整范围，再在点击时做目标存在性校验，符合提案。  
   - **备选**：仅高亮有目标的格子（当前行为）。不采纳，因无法满足「显示所有可攻击格子」的需求。

2. **点击范围内空格子的行为**  
   - **决策**：玩家点击攻击/技能后，若点击的是范围内但无目标的格子，不执行攻击/技能；可保持高亮直到玩家点击其他格子或取消，或视为取消当前攻击/技能选择。具体交互（取消方式）由实现与 UI 约定。  
   - **理由**：提案明确「只有格内有目标时才生效」，空格子点击不触发攻击。

3. **棋将包数据来源与展示**  
   - **决策**：棋将包可选列表从 `GeneralConfigLoader.LoadHeroConfigs()` 取得；展示时用 HeroConfig 的 ID、形象路径（立绘）等；若需「本关可用」子集，可由调用方传入 ID 列表过滤，默认可用全表。  
   - **理由**：与 OPENSPEC 约定一致，配置驱动；扩展子集时只需在布阵入口传入 ID 列表即可。

4. **布阵区域与拖拽规则**  
   - **决策**：布阵仅允许放置到地图第 1 列（col=1）或第 2 列（col=2）的格子；每格最多一个棋将；拖拽来自棋将包，放下后该棋将从包内移除或标记为已使用，本场战斗不可再次拖拽上场。  
   - **理由**：提案限定「第 1 列或第 2 列」；每战每棋将仅上场一次，避免重复布阵同一棋将。

5. **「确认出战」与战斗开始**  
   - **决策**：布阵阶段不启动回合与怪物 AI；玩家点击「确认出战」后，将当前已布阵的棋将视为本局我方单位，关闭或隐藏棋将包/拖拽，并触发现有「战斗开始」逻辑（如回合开始）。  
   - **理由**：与现有回合/战斗流程衔接；布阵与战斗两阶段清晰分离。

6. **棋将包与布阵的 UI 归属**  
   - **决策**：棋将包 UI（列表/卡片 + 拖拽源）可放在 FightBoard 场景下方或独立子场景，由 FightBoard（或主战斗场景）加载；布阵目标区域为棋盘第 1/2 列的格子，复用现有格子点击/放置逻辑，增加「是否处于布阵阶段」与「是否允许放置」判断。  
   - **理由**：FightBoard 已管理格子与单位放置，布阵本质是「在限定列放置棋将」，归属同一场景便于管理状态。

## Risks / Trade-offs

- **[风险] 高亮所有范围格可能导致大范围时视觉杂乱**  
  → 缓解：保持与「有目标格子」不同的高亮样式（若需要）由实现决定；规格仅要求「所有范围格子均高亮」。

- **[风险] 布阵阶段与现有 TestScene 直接生成棋将的兼容**  
  → 缓解：TestScene 或战斗入口改为先进入布阵阶段，从包中拖拽布阵再确认出战；若保留「跳过布阵」的测试路径，可约定为直接使用某默认 ID 列表并自动放置，不显示棋将包。

- **[trade-off] 棋将包仅从 General.xlsx 全表加载**  
  → 接受：本变更不强制关卡配置「可用棋将」子集；若后续需要，可在关卡数据中增加 ID 列表并在布阵时过滤。

## Migration Plan

- 实现顺序建议：先做「攻击范围高亮与执行判定分离」，再做「棋将包 + 布阵 + 确认出战」；两者可独立测试。
- 回滚：恢复高亮仅使用「范围内有敌将」的格子即可恢复原行为；布阵阶段可通过入口开关跳过，保留直接生成棋将的路径直至新流程稳定。

## Open Questions

- 无。若后续需要「本关可用棋将」子集，可在关卡配置中增加字段并在布阵时过滤 LoadHeroConfigs 结果。
